# Tower Pulse

Tower Pulse is the planned public analytics surface for Tower Map.

The goal is to turn the tower's own activity into a readable public signal:
which tenants are being saved, which profiles are collecting notes, which
floors are heating up, how the registry is distributed, and how contract
verification is progressing.

Tower Pulse should feel like a building status board, not a trading terminal.

## Source Snapshot

The first Tower Pulse layer reads:

```text
reports/analytics-snapshot.json
```

That snapshot is generated by:

```bash
npm run analytics:snapshot
```

The source model is documented in `docs/analytics.md`.

The first web implementation path is documented in
`docs/tower-pulse-implementation.md`.

## First Page Sections

The first public page can be built from five sections:

- Tower overview
- Most saved tenants
- Most discussed tenants
- Hottest floors
- Registry composition
- CA verification progress

## Tower Overview

The overview should show the current shape of the tower:

- total tenants
- total floors
- total categories
- total public saves
- total public notes
- current hottest floor

This gives visitors a quick sense of whether the building is quiet, active, or
changing.

## Tenant Signals

Most saved tenants and most discussed tenants should be shown as editorial
signals, not investment rankings.

Copy should avoid:

- "top coins"
- "winners"
- "buy"
- "pump"
- "guaranteed"

Preferred copy:

- "Most saved residents"
- "Most discussed rooms"
- "Attention currently gathering around..."
- "Profiles collecting public memory"

## Floor Signals

Hottest floors combine registry heat with saves and Tenant Notes. The page
should explain that floor heat is an internal Tower Map signal, not a price
metric.

Good labels:

- "Active floors"
- "Floors with the most public signal"
- "Where the building is loudest today"

## Registry Composition

Category distribution should show the shape of the curated registry:

- which wings are most populated
- which categories collect saves
- which categories collect discussion
- which areas may need future review

This section helps Tower Map look like an inspectable editorial system, not a
random list.

## CA Verification Progress

The verified CA ratio should be shown honestly.

Pending verification is maintenance data. It means Tower Map has not confirmed
the address from an official source or trusted registry yet.

Recommended copy:

```text
Contract addresses are displayed only after verification.
Pending is explicit maintenance status, not hidden data.
```

## Page Route

Recommended route:

```text
/pulse
/en/pulse
/ja/pulse
```

The page can start as a static route that imports
`reports/analytics-snapshot.json`. Later it can move to a server route or
Supabase-backed aggregate query.

## Design Notes

Tower Pulse should use the same editorial architecture as the rest of Tower
Map:

- restrained color
- strong labels
- compact tables or rows
- no casino-style charts
- no price candles
- no oversized dashboard cards

The page should feel like looking at the building's lobby signal board.

## Release Readiness

Before shipping Tower Pulse:

- `npm run analytics:snapshot` should pass.
- Snapshot slugs should match the current tenant registry.
- Empty or missing interaction fields should have readable fallback states.
- The page should link back to the tower and methodology.
- Public copy should distinguish Tower Map signal from market data.

Implementation details live in `docs/tower-pulse-implementation.md`.
